# 业务逻辑调研

## 调研方法

为精确把握校园卡服务的真实业务逻辑与潜在痛点，本项目小组采用“流程沉浸法”，对暨南大学现行的校园卡充值流程进行了端到端的亲身体验与深度拆解。调研发现，该校的校园卡充值入口集成于“暨南大学”官方微信公众号的“微服务”模块下的“实体校园卡服务”中。该服务支持“卡账户”与“场馆电子账户”两类钱包，支付通道目前仅开放了微信支付及绑定银行卡支付。
![[卡片充值页面.jpg|360]]

支付时收款方显示为暨南大学学校全称，即学校对公基本户。
![[收款方.jpg|360]]

## 核心发现：充值流程的特殊性

调研中我们发现了一个关键的、区别于一般线上支付认知的流程——“过渡余额”机制。
![[充值成功页面.jpg|360]]

其完整路径如下：

- **支付完成不等于余额增加**：用户通过微信支付成功将资金转入学校对公账户后，该笔金额并不会直接累加到校园卡的可用余额中。
- **资金暂存**：充值金额首先进入一个名为“过渡余额”的中间状态。
- **线下激活**：系统提示用户必须前往校内任一食堂的消费POS机上进行刷卡操作，该操作成功后，“过渡余额”才会正式划转为可用于消费的“校园卡余额”。

## 调研结论

- 资金流：
	用户资金 -> 微信支付 -> 学校对公基本户 -> 校园卡系统接收微信支付成功的异步通知 -> 系统为该用户校园卡账户写入“过渡余额” -> 用户在校内POS机刷卡 -> 系统将“过渡余额”划转为“校园卡余额”。
- 信息流
	微信支付平台生成支付成功报文 -> 通过API回调接口，将该报文（含订单号、金额、时间等）发送至校园卡系统 -> 校园卡系统验证报文合法性 -> 系统将“充值成功”状态及“待领取金额”推送给前端 -> POS机刷卡时，卡内芯片与后台系统交互，发起圈存指令 -> 系统验证通过，更新数据库中的余额字段，并记录该笔交易流水。
- 关键事实：
	校园卡系统在整个资金流转过程中扮演的是纯粹的“账本”角色，它负责记录和更新用户的权益（余额），但从不实际持有、管理或操作学校的实体银行资金。

# 问题描述与术语定义

## 术语定义

为使本文表述精确、无歧义，现将本项目涉及的核心术语定义如下表所示。该定义同时参考了对暨南大学的实际业务调研。

| 术语                           | 定义                                                                            |
| ---------------------------- | ----------------------------------------------------------------------------- |
| **校园卡 (Campus Card)**        | 由校方统一发行的、集成身份认证与电子支付功能于一体的媒介。它既是物理实体卡，也可以是App内的虚拟卡。其关联账户内的资金权益仅限于校内指定场景的消费。   |
| **校园卡余额 (Card Balance)**     | 记录于校园卡后台账户中的、代表用户可用于直接消费的货币价值单位。调研显示，此余额具有**不可兑现、不可退款**的属性。                   |
| **过渡余额 (Interim Balance)**   | 特定于现有流程中的一个临时资金状态。用户线上支付成功后，资金首先进入此状态，需经过线下POS机刷卡圈存后，方能转化为“校园卡余额”。本项目旨在消除此状态。 |
| **对公账户 (Corporate Account)** | 校方在银行开立的、用于归集所有用户校园卡充值款项的法定实体账户。本系统对其无任何操作权限，仅通过银行或第三方支付平台接口获取资金到账的凭证。        |
| **充值 (Top-up)**              | 指用户通过本系统发起，经由外部支付平台完成资金转移，并最终增加校园卡账户余额的完整服务过程。                                |
| **支付回调 (Payment Callback)**  | 第三方支付平台在用户成功完成支付动作后，向其对接的服务商系统发起的一个异步HTTP请求。该请求用于通知服务商，一笔支付交易已正式生效。           |

## 问题描述

### 背景

据调研观察，暨南大学校园卡的持有率接近100%，是全校师生身份识别与校内消费不可或缺的基础设施，其应用覆盖食堂餐饮、超市购物、图书馆门禁等关键场景。然而，高持有率并未转化为高使用率，其深层原因在于现行的线上服务流程存在显著的用户体验断点。

### 现有痛点

- **支付通道单一**：目前仅支持微信支付，不支持拥有庞大用户基数的支付宝，限制了用户的选择自由。
- **充值流程存在线下断点**：最为突出的痛点是“过渡余额”机制。用户在移动端完成便捷支付后，却被强制要求前往线下POS机“刷卡圈存”，这一流程将原本高效的线上服务又拽回了线下，极大地削弱了移动应用的核心价值，造成了用户体验的割裂。
- **即时性体验缺失**：从线上支付成功到线下可刷卡消费之间存在的时间与空间延迟，无法满足用户对“即时到账、即时可用”的心理预期。

### 项目目标

基于上述痛点，本项目旨在设计并描述一个新一代的“校园卡服务系统（CCSS）”。其核心目标是摒弃“过渡余额”这一过时的线下确认环节，**重塑一个纯线上、多渠道、即时到账的闭环体验**，将校园卡服务从“可用”提升至“好用”，显著增强师生使用的意愿与粘性。

# 建议的解决方案

## 方案概述

为彻底解决现有流程中的线下断点问题，我们建议设计一个基于B/S架构的移动Web应用——CCSS。该系统的核心理念是 **“支付即到账”** 。我们主张，当用户通过微信或支付宝完成支付的那一刻起，用户与系统的交互闭环就应在线上全部完成，无需任何额外的线下操作。

## 核心业务逻辑重构

本方案对现有流程的核心变革，在于**消除“过渡余额”状态**。新的业务流程将重构如下：

1. **用户发起**：用户在CCSS App内选择充值金额和支付方式（微信/支付宝）。
2. **平台支付**：系统调用第三方支付SDK，用户完成身份验证和支付，资金转入学校对公账户。
3. **回调确认**：系统后端接口接收到微信/支付宝的支付成功回调报文，并验证其合法性。
4. **余额直充**：验证通过后，系统不再创建“过渡余额”，而是**直接且原子性地**增加该用户校园卡账户的可用余额。
5. **实时反馈**：前端页面实时更新余额，并向用户推送“充值成功，XX元已到账”的通知。

## 系统边界与职责定义

为保证项目范围清晰，我们在此明确界定CCSS的职责边界：

- **系统负责**：
    - 管理用户与校园卡账户的数字信息。
    - 集成并维护与微信、支付宝支付网关的可靠对接。
    - 处理支付回调，执行增加用户余额的核心记账逻辑。
    - 记录所有交易的完整、不可篡改的流水。
    - 提供用户查询余额、消费记录的前端界面。
- **系统不负责**：
    - 处理、持有或划拨任何实体资金。
    - 操作学校的银行对公账户。
    - 处理任何形式的提现、退款或资金转出请求。
